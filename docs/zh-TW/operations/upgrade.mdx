先備份並記錄目前的部署，再檢查版本差異、套用新版設定並驗證登入與權限。需要回復到舊版時，依資料相容性選擇切回舊映像檔或還原升級前的備份。

### 目前不保證的事

Zeabur Identity 目前是 alpha，沒有升級與回復保證。資源版本仍是 `v1alpha1`，版本之間沒有轉換機制。在發行說明明確承諾前，不要假設任何方向的版本切換都能成功。記錄實際執行的完整 commit 與映像檔，不要只記錄會重複使用的標籤，例如 `zeabur-identity:dev`。

`kubectl rollout undo` 只會回復 Pod 範本，不會回復 CRD、使用者、簽署金鑰、Secret、RBAC、Service、Ingress 或 kube-apiserver 的檔案。新版 Zeabur Identity 寫入資料後，不保證舊版能讀取。

Zeabur Identity 執行單一副本，更新時會替換副本，不採滾動更新。升級會短暫中斷服務，當時正在登入的使用者必須重新登入。不要增加副本來掩蓋中斷。

## 升級前

<Steps>

<Step>

### 確認緊急入口並備份

確認[不經過 Zeabur Identity 的入口](./emergency-access.mdx)能正常使用，再依[備份與還原](./backup-restore.mdx)建立完整備份。

記錄備份時間。還原這份備份時，你會失去備份之後的資料。

</Step>

<Step>

### 記錄目前的部署

記錄來源 commit、`zeabur-identityctl` 版本，以及安裝時使用的所有選項，包括 Issuer、Namespace、映像檔、每個 `--serve-arg`、`--config-secret` 和所有 overlay。讓每個節點都保留可用的舊映像檔。

執行以下指令，保存目前的部署資訊。這些檔案必須保密。

```sh
umask 077
NS=zeabur-identity
mkdir -m 0700 upgrade-record
kubectl -n "$NS" get deployment zeabur-identity -o yaml > upgrade-record/deployment.before.yaml
kubectl -n "$NS" get pods -l app.kubernetes.io/name=zeabur-identity \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.name}{"\t"}{.image}{"\t"}{.imageID}{"\n"}{end}{end}' \
  > upgrade-record/image-identities.before.txt
kubectl -n "$NS" rollout history deployment/zeabur-identity > upgrade-record/rollout-history.before.txt
```

這些檔案只是部署紀錄，不是備份。

</Step>

<Step>

### 準備新版映像檔

使用 digest，或指向已知 commit 且不會重複使用的標籤。將映像檔載入所有能執行 Zeabur Identity 的節點。

</Step>

<Step>

### 準備新版資源清單

使用新版 `zeabur-identityctl`，搭配原本的安裝選項，將新版資源清單產生到檔案，再與目前的部署比較。不要將使用新版預設值產生的資源清單直接以管線送進叢集。

</Step>

<Step>

### 檢查版本差異並試升級

閱讀兩個版本之間的變更，包括 CRD schema、儲存格式、選項與權杖宣告。

先在還原的副本上測試完全相同的升級流程，也要使用既有通行密鑰登入。

</Step>

<Step>

### 決定回復方式

如果無法確認舊版能讀取新版資料，回復方式就是還原先前的備份，並接受備份之後的資料損失。

如果資料需要遷移，但沒有遷移方式，就不要升級。

</Step>

</Steps>

## 升級

<Steps>

<Step>

### 產生升級檔案

將前四行換成你的設定值。以下 `manifests` 指令與[在 k3s 上安裝並登入](../get-started/quickstart.mdx)相同，會啟用邀請功能。補上安裝時使用的所有選項；如果原本沒有啟用邀請功能，移除 `--serve-arg=--invitations`。

```sh
NS=zeabur-identity
NEXT_ZEABUR_IDENTITYCTL=/path/to/new/zeabur-identityctl
NEXT_IMAGE=registry.example.test/zeabur-identity@sha256:...   # the new image, by digest
ZEABUR_IDENTITY_ISSUER=https://identity.example.test
"$NEXT_ZEABUR_IDENTITYCTL" crds > upgrade-record/crds.next.json
"$NEXT_ZEABUR_IDENTITYCTL" manifests --issuer "$ZEABUR_IDENTITY_ISSUER" --namespace "$NS" --image "$NEXT_IMAGE" \
  --serve-arg=--invitations > upgrade-record/manifests.next.json
# Leave out the empty signing-key Secret: it's only for new installs.
jq '.items |= map(select(.kind != "Secret"))' upgrade-record/manifests.next.json \
  > upgrade-record/manifests.upgrade.json
```

</Step>

<Step>

### 檢查並套用資源清單

套用前，閱讀 `upgrade-record/crds.next.json` 與 `upgrade-record/manifests.upgrade.json`。

如果套用時出現衝突，先找出原因，不要加上 `--force-conflicts`。不要為了排除錯誤而刪除並重建 CRD，這會刪除該類型的所有物件。

```sh
kubectl apply --server-side -f upgrade-record/crds.next.json
kubectl apply --server-side -f upgrade-record/manifests.upgrade.json
kubectl -n "$NS" rollout status deployment/zeabur-identity --timeout=5m
kubectl -n "$NS" logs deployment/zeabur-identity --tail=200
```

保留 `zeabur-identity` Service、`zeabur-identity-internal-ca` 與 `zeabur-identity-signing-keys`，不要替換。新 Service 不保證沿用原本的 IP，而每個 kube-apiserver 的驗證檔案都固定使用舊 IP。

不要在升級時替換根 CA、變更 Issuer 或刪除工作階段。如果新版確實需要不同的 kube-apiserver 設定，將它視為獨立變更，一次處理一台機器。

</Step>

<Step>

### 確認升級結果

檢查實際執行的映像檔、就緒狀態與日誌，再完成以下驗證：

- 使用既有通行密鑰重新登入。
- 嘗試一項有權限的操作與一項沒有權限的操作。
- 確認管理員存取正常。

Pod 就緒不代表登入功能正常。

</Step>

</Steps>

## 回復

<Steps>

<Step>

### 停止不確定的資料寫入

如果無法確認新版寫入了哪些資料，先停止 Zeabur Identity，避免它繼續寫入：

```sh
kubectl -n zeabur-identity scale deployment/zeabur-identity --replicas=0
```

</Step>

<Step>

### 依資料相容性選擇回復方式

#### 舊版能讀取目前的資料

只有在確認舊版能讀取目前資料時，才切回舊映像檔。

如果只變更映像檔，執行：

```sh
kubectl -n zeabur-identity set image deployment/zeabur-identity zeabur-identity="$PREVIOUS_IMAGE"
```

如果還有其他 Pod 範本變更，先檢查修訂紀錄：

```sh
kubectl rollout history deployment/zeabur-identity --revision=N
```

再回復到指定修訂版本：

```sh
kubectl rollout undo deployment/zeabur-identity --to-revision=N
```

手動回復其他變更，再恢復副本數。

#### 無法確認舊版能讀取目前的資料

依[備份與還原](./backup-restore.mdx)的還原流程，還原升級前的備份，搭配舊映像檔、資源清單、CRD 與 Secret。還原期間保持 Zeabur Identity 停止。

你會失去備份之後的所有變更，包括新增的通行密鑰、群組變更、用戶端更新與金鑰輪替。

<Callout type="warn">

還原備份會帶回備份中已撤銷的工作階段與已使用的邀請。重新開放服務前，先刪除這些工作階段與邀請。

</Callout>

不要為了啟動舊版而安裝空的簽署金鑰 Secret、刪除憑證或發出新的設定連結。

</Step>

<Step>

### 確認回復結果並記錄損失

檢查映像檔、就緒狀態與日誌，再重新登入。確認一般存取、管理員存取與緊急入口都正常。

記錄還原了哪些內容，以及損失了哪些資料。

</Step>

</Steps>
